## 1. Executive Summary

Campus Marketplace is a **well-structured React + Supabase application with a sound security model**. Authorization lives in the database:
- Row Level Security (RLS) is enabled on every table;
- ownership is enforced with `auth.uid()`;
- storage paths are scoped to the owner's folder;
- CHECK constraints mirror the form validation.

Nothing in the frontend acts as the only line of defence.

Everything a logged-out visitor can do, I tested in the browser and against the live API:
- browse, search, filter, sort and paginate;
- open a listing; handle missing listings;
- get redirected from protected routes;
- see form validation fire;
- load on phone-size screens.

All of it worked. No secrets are exposed. `npm audit` reports 0 vulnerabilities. The type-check and build pass.

**The main gaps are production hardening, not broken features:**
1. **Email confirmation is off** (verified through the public auth settings endpoint), so anyone can register with any email address and any campus name.
2. **There is no password reset**, so a user who forgets their password is locked out for good.
3. **The production database holds the 50 seeded demo accounts and 74 demo listings.**
4. **Clients can backdate or future-date `created_at`** on new listings, chats and messages, which lets a seller pin a listing to the top of "Newest" forever.
5. **There are no automated tests** and no `npm test` script.
6. **Scale limits:**
   - category counts download every row and are silently capped at 1,000;
   - "Load more" re-downloads everything already loaded;
   - every listing change makes every open browser re-query;
   - search uses unindexed `ILIKE '%…%'`.
7. **Deployment:**
   - no security headers;
   - after each redeploy, any user with an old tab open breaks: a missing old chunk is served as HTML with status 200;
   - the free Supabase project pauses when idle;
   - the new landing page is neither committed nor deployed.

**Verdict:** ready to demo as a student project. **Not ready for real students** until the P0 items in §20 are fixed.

## 5. Critical Bugs

**None in the security sense.** I found no way for one user to read or change another user's data, and authorization is enforced in the database.

The **highest-impact defects** for a real launch are:
1. **No email verification** (`mailer_autoconfirm: true`). Anyone can register as `anyone@college.edu` and claim any campus. This is a trust and impersonation risk on a peer-to-peer money marketplace.
2. **No password reset.** A forgotten password means a permanently lost account, including its listings and chats.
3. **Demo data in production.** Fifty fake student accounts and 74 fake listings would mislead real users.
4. **Client-controlled timestamps.** `created_at` is writable on insert (§6.2).
5. **Deploy breaks open sessions** (§4 #1).

## 7. Database Findings

**Schema quality: good.**
- Primary keys, foreign keys with `on delete cascade`, and enums for category and status are all in place.
- CHECK constraints mirror the UI: title 3–100, description 10–2000, price 1–1 crore, 1–5 images, latitude/longitude ranges, message 1–2000, `buyer_id <> seller_id`.
- The composite PK on `favorites` and `unique (listing_id, buyer_id)` on `chats` prevent duplicates.
- Trigger functions use `security definer set search_path = ''`, which is the correct hardening.

| Topic | Finding | Status |
|---|---|---|
| Indexes present | `listings(status, created_at desc)`, `(category)`, `(price)`, `(seller_id)`; `favorites(listing_id)`; `chats(buyer_id)`, `(seller_id)`; `messages(chat_id, created_at)`, `(sender_id)` | ✅ reasonable |
| Missing index: text search | `ILIKE '%q%'` on `title` + `description` can't use B-tree indexes → sequential scan | 💡 `pg_trgm` GIN or a `tsvector` column + GIN |
| Missing index: filtered sorts | `category + status + created_at` and `status + price` combos | 💡 composite indexes at 10k+ rows |
| Possibly redundant | `listings_category_idx` alone is weak (10 values); `messages_sender_idx` serves only FK cascades | Keep for FK deletes; low priority |
| Timestamps | Insert-time `created_at` client-writable | 🔴 see §6 |
| Cascade on listing delete | Deleting a listing silently deletes the buyer's chat history | 💡 Soft-delete listings (`deleted_at`) or `set null` + "Listing removed" (the UI already has that text) |
| Sold listings | DB allows new chats/messages on sold listings; the UI hides "Contact Seller" | Acceptable; document it |
| Orphans | DB orphans impossible (FK cascades). **Storage** orphans possible: upload-then-insert, and post-delete cleanup is best-effort client-side | 💡 Scheduled cleanup |
| Realtime | `listings`, `chats`, `messages` in `supabase_realtime`; RLS applies to `postgres_changes` | ✅ subscriptions live; event filtering ☑️ via design |
| Race conditions | `getOrCreateChat` handles a `23505` race; favourites handle `23505`; listing insert uses client UUID | ✅ handled in code (🟡 not run) |
| Unused field | `profiles.avatar_url` is never read or written by the app (UI uses initials) | 💡 Remove or implement avatars |
| Types | No generated DB types; services use `as unknown as` casts | 💡 `supabase gen types typescript` |

## 9. Backend Findings

There is no custom server; Supabase is the backend. Observations:
- **Service layer is clean.** Every query goes through `src/services/*`. Errors are normalised by `toUserMessage()`, and RLS "0 rows" is turned into `NOT_ALLOWED`.
- **Multi-step operations aren't atomic.** Create = upload images, then insert; edit = upload, update, then delete removed files; delete = delete row, then remove files. Failures are compensated client-side (`removeImages(...).catch(() => {})`), but a closed tab or network drop between steps leaves orphaned files.
  - 💡 Move cleanup to an Edge Function, or a scheduled job comparing `storage.objects` with `listings.image_paths`.
- **No server-side business rules beyond constraints:** no rate limits, quotas or moderation hooks.
- **Geocoding runs from the browser to the public Nominatim server.** Its usage policy forbids heavy or bulk use. Fine for a demo; a real launch needs a commercial geocoder or a self-hosted instance.

## 10. Performance Findings

**Measured:**
- Home query (20 rows + exact count): about 213 ms.
- Search query: about 172 ms (network-dominated).
- Seeded images: about 38 KB PNG each, served with `cache-control: no-cache`. App uploads set a 1-year cache.
- JavaScript, gzipped: about 70 KB index + 57 KB supabase-js + 61 KB React DOM + 10 KB App + 14 KB landing ≈ **210 KB** for a logged-out first visit.

**Not measured:** Lighthouse and real-device performance.

| Issue | Where | Effect |
|---|---|---|
| "Load more" re-fetches rows 0..N every time | `useListings.ts:33` (verified: 2nd page request was `offset=0 limit=40`) | Viewing 100 cards downloads 300 rows |
| Every client refetches on **any** listing change | `useListings.ts:64` | With 500 open tabs, one new listing triggers 500 queries |
| `count: 'exact'` on every feed query | `listingService.ts:24` | Full count scan per request at large sizes |
| Category counts download all rows | `listingService.ts:142` | O(n) payload; capped at 1,000 rows, so wrong counts above that |
| Unindexed `ILIKE '%…%'` on two text columns | `listingService.ts:27` | Sequential scan per search |
| No thumbnails | `ListingImage.tsx` | Cards download full-size (≤ 1600 px) images |
| Render blocked until 5 dynamic imports resolve | `main.tsx:22` | Blank page until JS loads; no HTML skeleton |
| Realtime `postgres_changes` checks RLS per change per subscriber | Supabase design | Known bottleneck past a few hundred subscribers |

### Scale estimates

| Listings | Expected behaviour |
|---|---|
| **100** | Everything fast. No issues. |
| **1,000** | Still fine. Category counts hit the 1,000-row cap and begin to undercount once available listings exceed it. Scrolling deep through "Load more" re-downloads hundreds of rows. |
| **10,000** | **Category counts wrong** and heavy (10k rows per landing visit). Search via sequential scan is still tens of ms, but `count: exact` + realtime refetch storms start to matter. Storage: about 30k images × 150–300 KB ≈ **5–9 GB**, far beyond the free plan's storage and egress (check current Supabase plan limits). |

## 11. UI/UX Findings

**Score: 7.5 / 10.** The playful neubrutalist style is distinctive and consistent:
- Material 3 colour roles throughout;
- thick ink borders and pop shadows;
- Fredoka/Nunito type.

It reads as a designed product, not a template. Forms give clear inline errors, confirmations use a real dialog, toasts give feedback, and skeletons and empty states exist everywhere I checked.

**What holds it back from "real marketplace":**
1. **Demo imagery.** Every listing uses an illustrated placeholder, not a photo. Real data would fix this, but the cards should be designed for real photos (aspect ratio, cropping).
2. **No unread badges or notifications.** Buyers don't know a seller replied unless they open Messages.
3. **No seller profile page.** You can't see a seller's other listings, join date or response rate. Trust is the core problem in peer-to-peer selling.
4. **No item condition field** (new / like new / used), and no "price negotiable" option.
5. **No safety guidance** at the moment it matters (in chat: meet in public, inspect before paying), and **no "Report listing"**.
6. **No sharing.** No share button, and no per-listing Open Graph tags, so links pasted into WhatsApp show a generic preview.
7. **Location is free text plus an optional pin.** No list of campus landmarks to pick from.
8. **Small issues:** the inline auth links are under 24 px tall; the gallery has no swipe or keyboard navigation; nothing guards unsaved edits.

## 17. Technical Debt

1. **No automated tests or CI.** The biggest debt.
2. **No generated Supabase types.** `as unknown as` casts in `chatService.ts` and `favoriteService.ts` hide schema drift.
3. **Reset-then-fetch `useEffect` pattern** repeated in 11 places (lint `set-state-in-effect`). A small `useAsync` hook or TanStack Query would remove the duplication and add caching.
4. **Pagination by re-fetching from 0.** Switch to offset or keyset append.
5. **Non-atomic multi-step writes** (upload / insert / cleanup) in client code.
6. **Dead code:** the "Listing removed" branch in chat UI; unused `profiles.avatar_url`.
7. **Mismatched messages:** `weak_password` says 6 characters, the UI enforces 8.
8. **Vendored engine** (`src/landing/engine/scrollcraft.js`, about 1,300 lines) with 11 lint warnings. Intentionally unmodified; exclude it from lint.
9. **Uncommitted work:** the landing redesign, M3 token generator and Navbar change are staged but not committed.
10. **Manual QA sheet** (`docs/TEST_RESULTS.md`) never filled in beyond RLS.

## 18. Recommended Fix Order

1. Commit the reviewed working tree, so the audit baseline is in git.
2. Supabase Auth: custom SMTP → enable "Confirm email" → minimum password length 8 → leaked-password protection.
3. Add the password reset flow.
4. Migration: `BEFORE INSERT` trigger forcing `created_at`/`updated_at` = `now()` (listings, chats, messages, favourites); revoke anon write privileges.
5. `vercel.json`: security headers; stop rewriting `/assets/*`; chunk-load-error reload + a top-level error boundary.
6. Fix `getCategoryCounts` (RPC with `group by`) and "Load more" (append only).
7. Add Vitest + Playwright with the §12 matrix; run rls-test in CI against a staging project.
8. Before real users: you remove the demo data (the cleanup SQL from earlier); set up a keep-alive or upgrade the plan.
9. Then features: unread counts → report listing → seller profile → condition → share/OG.
